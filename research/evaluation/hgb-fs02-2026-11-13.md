# hgb-fs02-2026-11-13: the gateway's first trained model

Built on 13 Nov 2026 for MVP sprint 7 by `research/training/train_gateway_model.py`. This is
the **integration model**: it shows the gateway running a real HistGradientBoosting artefact on
the features it can compute itself (schema fs-0.2). It is not the fraud experiment's result.
The experiment (team folder `02-research/fraud-experiment`, owner Noppawut) answers the
research question with richer IEEE-CIS inputs. Its final period (days 147+) was evaluated once
on 13 Nov 2026 and is now consumed (result: inconclusive, see its STUDY-CONCLUSION.md); this
model never read it, and it must not become a tuning resource.

One-page summary for the report: [`MODEL-CARD-hgb-fs02-2026-11-13.md`](MODEL-CARD-hgb-fs02-2026-11-13.md).

| Item | Value |
| --- | --- |
| Data | IEEE-CIS `train_transaction.csv`, days 0 to 146 only (487,837 rows). Days 147+ are the experiment's final period and were cut out before the data left the team folder. |
| Splits | fit days 0-110 (383,118 rows, 3.42% fraud); tune days 111-128 (56,900); report days 129-146 (47,819), unseen by fitting and threshold choice |
| Model | `HistGradientBoostingClassifier(max_iter=300, max_leaf_nodes=31, min_samples_leaf=50, learning_rate=0.1, l2_regularization=10)`, chosen over the experiment's baseline setting by average precision on the tune days (0.1134 vs 0.1108) |
| Features (9) | `amount_cents`, `card_attempts_10m`, `card_attempts_1h`, `card_attempts_24h`, `card_attempts_7d`, `card_attempts_30d`, `card_seconds_since_last`, `card_mean_amount_30d`, `amount_to_card_mean_30d` |

| Not used | `email_*` and `ip_*` (IEEE-CIS has no email address or IP), `card_blocked_24h`, `card_allowed_30d` (no screening outcomes in the data), `card_distinct_emails_24h` |
| scikit-learn | 1.7.2 (same as the gateway) |
| SHA-256 of model.joblib | `a7dee1a5216750205b2c731ac7d5874a3ec0f5e1f72c17b57ebddd770e41ec5e` |

## How to read this

* The model is weak. The experiment's current-transaction HGB reached ROC-AUC 0.81 on its
  tuning period (0.79 on its final period) with inputs the gateway does not collect (product code, card network and type,
  email domain, address). Collecting those is a feature-schema change for a later sprint.
* IEEE-CIS amounts are USD; the gateway reads them as SGD cents. Card attempts in IEEE-CIS are
  processed transactions, while the gateway counts every screening attempt, including blocked
  ones. Both are known mismatches, so live scores are indicative only.
* Development numbers, single run, no uncertainty interval. Not a claim about real fraud rates.

## Against the experiment's feature-correctness handover (13 Nov 2026)

The fraud experiment's handover (`02-research/fraud-experiment/FEATURE-CORRECTNESS-HANDOVER.md`)
sets acceptance cases for any online feature builder. Where this gateway stands:

| Case | Status |
| --- | --- |
| Window `[t - w, t)`, strictly earlier events, same-time events do not see each other | Same rule in SQL and in `gateway_schema.py`; parity test with ties and window edges |
| Golden vectors | `research/features/fixtures/experiment-golden-vectors-2.0.json` (synthetic). `test_parity.py` checks the replay and the SQL against the 7 history values that map onto fs-0.2 |
| A retry never counts twice | One `ScreeningEvent` per payment (one-to-one); a retried submission reuses it |
| Crash before commit leaves no history | The event is written in the checkout transaction, so a rollback removes it |
| Concurrent submissions | Insert-only history, no lost updates; two attempts on one card at the same moment may not see each other, like the same-time rule |
| Merchant scope | Card, email and IP history is counted **across all merchants** (gateway-wide, as card networks do), so a card tried at one shop is seen at the next. Decided by Fifa on 13 Nov 2026: the gateway protects every merchant and customer. Only keyed fingerprints and hashes are shared; no merchant sees another's payments |
| Do not reuse the benchmark model with the card fingerprint | Not done: this model is trained on the gateway's own schema, and the card-key mismatch is stated above |

The experiment's exploratory finding that card amount moments help when gated until five
earlier observations is not used here; it is a candidate for the next schema.

## Latency (NFR-PER-02)

`manage.py loadtest_screening --rate 20 --seconds 60` on the Docker stack (gunicorn gateway,
Postgres 17, 4 vCPU cloud VM, 5,000 earlier screening events): 1,200 screenings at 20.0/s,
screening as checkout calls it p50 16.9 ms, **p95 21.6 ms**, p99 25.8 ms, max 118.5 ms; none over
the 500 ms budget. PASS against p95 <= 200 ms. With the stub model the same run gives p95 about
20 ms, so the model adds about 2 ms. Before `OMP_NUM_THREADS=1` (now set in
`gateway/config/settings.py`) the model's OpenMP threads oversubscribed the CPUs and p95 was
66 ms.
