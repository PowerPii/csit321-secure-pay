## What is in it

A payment gateway with fraud screening for simulated card payments, built for CSIT321
(FYP-26-S4-36): hosted checkout with emailed verification codes, a card vault (AES-256-GCM,
deleted after submission), a rules, model and policy fraud pipeline with explained decisions,
reconciliation of lost bank replies, captures, partial refunds, signed webhooks with a delivery
log, a staff dashboard with TOTP and backup codes, customer accounts, a demo shop, a payment
simulator, a public status page and a Node.js SDK. The URS defines 100 functional requirements
(62 Must, 32 Should, 6 Could); every one is built, and Table 4.6.2.1 keeps only PayNow, which
the team decided not to build.

## Known limitations

- **Email delivery states need the server set up.** The Resend webhook (PR #80) stays off
  (404) until `RESEND_WEBHOOK_SECRET` is in `deploy/.env` and the webhook is added in the
  Resend dashboard (RUNBOOK 13b step 5); until then emails stop at "sent". "Delivered" means
  the recipient's mail server took the message, never that a person read it.
- **People-run checks not done yet.** The first-time-user session
  (`FIRST-TIME-USER-SESSION.md`), the teammate recovery rehearsal (`docs/RECOVERY.md`), the
  "reviewed by" fields and the manual NFR checks still marked Pending above. NFR-USE-04 needs
  five people outside the team. No session with a screen-reader user has taken place.
- **Checkout speed not measured on the live server.** The NFR-PER-01 load test passed on a local
  stack (p95 85 ms) but the live run was stopped without a result, because the load generator
  shared the server's two vCPUs. It needs repeating from another machine.
- **Fraud result is inconclusive.** On the IEEE-CIS final holdout, combined history raised
  recall at the 1% false-positive line by 0.65 points (three-day-block 95% interval −0.39 to
  +1.88), and both frozen thresholds went over the 1% false-positive cap. The benchmark shows
  no reliable gain at the required operating point. The gateway's proxy features and the
  IEEE-CIS groupings differ, and the model is for simulated payments only.
- **Six Must checks ran on a disposable copy of the stack**, not the live server (by the
  team's choice), with the stub model; NFR-ENC-01 ran from the server itself. The screening
  timeout is recorded as `InternalError` in the decision record: the outcome (blocked as
  screening unavailable) is right, the label is vague.
- **Image digests are not reproducible across machines.** Images are built on the server, so
  their digests come from the deploy record, not from CI. There is no image registry.
- **No CI on this candidate and no branch protection.** Actions minutes run out until
  1 Dec 2026, and branch protection waits for GitHub Pro.
- **Status page numbers are small samples.** The "What payments experienced" figures come from
  the demo server's own traffic; with fewer than 20 timed payments the page shows the median,
  not the p95.
- **Security self-test.** No critical, high or medium findings remain; SEC-07b and SEC-08 are
  kept as documented limitations
  ([`SECURITY-SELF-TEST.md`](../test-report/SECURITY-SELF-TEST.md)).
- **npm metadata.** The registry reads the author's parenthesised text as a URL; fix in the
  next SDK release.
- **One host.** Capacity figures (checkout p95 195.6 ms at 20 payments/s over 6,000 payments)
  come from one host and one workload.

## Tagging and checking the candidate

After the pull request with this note is merged, on your Mac:

```bash
cd ~/Desktop/fyp/csit321-secure-pay   # or wherever your clone is
git checkout main && git pull
git log -1 --oneline                  # the merge commit of this note
git tag -a v1.0.0-rc.1 -m "SecurePay v1.0.0-rc.1 (release candidate; docs/releases/v1.0.0-rc.1.md)"
git push origin v1.0.0-rc.1
```

Then on the server (`ssh securepay@35.213.144.96`):

```bash
cd ~/csit321-secure-pay
git fetch origin --tags
bash deploy/auto-deploy.sh "$(git rev-parse 'v1.0.0-rc.1^{commit}')"   # exactly the tagged commit; runs the smoke check too
git describe --tags                              # must print v1.0.0-rc.1
bash deploy/release-record.sh show 1             # paste this into "Running image digests"
sha256sum gateway/apps/risk/model_artifacts/hgb-fs02-2026-11-13/model.joblib   # must match the model SHA-256
docker compose -f deploy/compose.prod.yaml run --rm integration-tests          # about 2 minutes; makes simulated test payments, not just before a demo
```

Record the integration run under `STACK` in `docs/test-report/manual-results.yaml` with the
tagged revision. Then turn on email delivery reports (RUNBOOK 13b step 5): add the webhook in
the Resend dashboard, put `RESEND_WEBHOOK_SECRET=whsec_...` in `deploy/.env`, and run
`docker compose -f deploy/compose.prod.yaml up -d gateway`. That changes configuration only,
not the tagged code.

If a fix is needed before the release, merge it, tag the next candidate (`v1.0.0-rc.2`) with
its own note, and never move an existing tag.
